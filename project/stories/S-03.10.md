# S-03.10 — Runner leans on built-ins

ADR-010 ("if Claude Code does it, Marcel uses it") and ADR-011. The runner already starts sessions with
`claude --bg --name` (S-03.2) and reads their state from `claude agents --json` (S-03.2, S-03.3). This story adds
the rest of what Claude Code offers for starting sessions, so nothing in the runner rebuilds it:

- Marcel's sessions load only Marcel's settings, never the owner's own `~/.claude/settings.json` (on the NUC it holds
  122 allow rules, broad Bash ones among them): `--setting-sources project,local` plus a role file passed with
  `--settings`;
- a worker runs as a named agent (`--agent`) that preloads the `worker-protocol` skill, if Claude Code allows it
  without losing its own system prompt;
- the runner refuses to start sessions on a Claude Code version Marcel has not been tested with, and deploy installs
  that exact version with auto-update off.

It runs on the NUC because step 2 is decided against the real `claude` there.

**Step 1 is split.** `--setting-sources project,local` on spawn, resume and fork shipped on its own (commit
"[S-03.10] impl: sessions load only project and local settings"), with its goldens, the inert-controls test
`runner/tests/test_setting_sources.py` and the lessons line on `~/.claude.json` MCP servers, because the live brain
was inheriting the owner's 122 allow rules. This story adds the `role_settings/` folder and `--settings`.

do:
1. **Only Marcel's settings.** Today every session the runner starts also loads the owner's user settings
   (`~/.claude/settings.json`), so the brain and the workers inherit the owner's allow rules. Claude Code's own
   answer (docs, checked 2026-10-13):
   - `--setting-sources project,local` leaves out the user settings file: its permissions, hooks, `env` and
     `enabledPlugins`, and also `~/.claude/CLAUDE.md`, user rules, skills, agents and commands (settings § settings
     files; agent-sdk/claude-code-features § settingSources). Managed settings and the `--settings` file still apply
     (managed-settings § where and when a policy applies).
   - Allow lists merge across files and a higher file cannot remove a lower file's allow (settings § lists merge),
     so a deny list alone cannot undo the owner's rules. Auto mode already drops `Bash(*)` and interpreter wildcards,
     but keeps narrow rules such as `Bash(git *)` (permission-modes § how auto mode evaluates actions).
   - A resume re-reads the settings files and does not restore `--settings` (sessions § what a resumed session
     restores), so every start passes both flags again.
   What the runner does:
   - `spawn_argv`, `resume` and `fork` add `--setting-sources project,local` for **every** role, before `--`.
   - A folder `runner/src/marcel_runner/role_settings/` with one JSON file per role that needs one. Today only
     `worker.json`:
     - `permissions.deny`: the same five restart commands as `brain/.claude/settings.json` (rule:
       self-modification). A worker in someone's repo must not restart Marcel either;
     - `"crossSessionInbound": "refuse"`: a worker is steered only through the hub and the channel, as the brain
       is (ADR-003);
     - nothing else. S-21.1 later adds `subagentPromptCacheTtl` to this file.
     `spawn_argv` adds `--settings <absolute path>` when a file for the role exists; `resume` adds the same for the
     recorded role. The brain and its side forks need none: `brain/.claude/settings.json` is their project settings
     and still loads, and it already enables the marcel plugin. A worker's clone enables the plugin at local scope
     (S-03.5), which still loads too. Claude Code reads the files; the runner only passes the path. A strict
     allowed-keys and allowed-values test checks `worker.json`, like `brain/tests/test_settings.py` (no settings
     schema is available offline).
   - Not chosen: `allowManagedPermissionRulesOnly` in the managed settings. It would apply to every session on the
     NUC, the owner's own included, and move all of Marcel's rules into a root-owned file. `--restricted` and
     `--bare`: they also drop the code tools or the plugin.
   - Still loaded, by design of Claude Code: MCP servers in `~/.claude.json` (agent-sdk § what settingSources does
     not control). Their tools still ask for permission under auto mode. The NUC note lists which ones a worker sees.
2. **Workers as a named agent.** First check, on the pinned version on the NUC, what `claude --agent <name>` does to
   Claude Code's own system prompt (docs: sub-agents § running as the main thread; then one real worker spawn).
   - **If the agent's prompt is added to Claude Code's own**: add `plugins/marcel/agents/worker.md` (name `worker`,
     a one-paragraph body: "You are a Marcel quest. Follow the worker-protocol skill.", frontmatter `skills:
     [worker-protocol]` so the skill is always loaded). `spawn_argv` adds `--agent <name>` for role `worker`, with
     the name in the form Claude Code gives a plugin agent (check it: plugins reference § agents). `resume` passes the
     same for a worker.
   - **If it replaces Claude Code's own prompt**: do not add `--agent`. Write one line in
     `project/lessons/runner-built-ins.md` saying why (ADR-010: one line why not), and leave the worker's opening
     prompt as it is.
3. **Pin the Claude Code version.**
   - `runner/claude-version` holds one line: the bare version number (e.g. `2.1.290`), the version installed on the
     NUC when this story starts. This is the only place the number lives. Today the fake claude and the test stubs
     say `2.1.289` (`fake_claude/shim.py`, `conftest.py`, `test_health.py`, `test_server.py`, `test_sessions.py`):
     make each of them read `runner/claude-version` instead, and give the fake claude an override
     (`MARCEL_FAKE_CLAUDE_VERSION`) so a test can make it report another version. The fake claude also accepts
     `--settings` and `--agent`, so the goldens can carry them.
   - **Deploy:** a new `deploy/install-claude.sh`, called by S-14.1's install step, installs exactly that version with
     Claude Code's documented installer (with its version argument). Turn auto-update off by adding
     `"DISABLE_AUTOUPDATER": "1"` to the `env` block of the managed settings S-14.1 installs
     (`deploy/managed-settings.json`, or the name S-14.1 gave it). Check both against the Claude Code setup and
     settings docs, and use what the docs name if it differs. `docs/operating.md` gets a short "Upgrading Claude Code"
     section: change `runner/claude-version` in a PR, run `make -C runner check` and the live tests (S-03.8), then
     deploy.
   - **Runner:** `collect_health` compares the number in `claude --version` (it prints `2.1.290 (Claude Code)`) with
     the pin. On a mismatch, `ok` is false, `claude_version_expected` is the pin, and `reason` says, in plain words,
     for example: "Claude Code 2.1.301 is installed, but Marcel is tested with 2.1.290. Install 2.1.290, or test the
     new version and change runner/claude-version." When the supervisor is also wrong, `reason` names both.
   - **Start-up:** a version mismatch alone does not stop the runner. It prints the same line and keeps serving
     `/health`, so the hub and the app can show it. A missing or wrong supervisor still stops start-up, as today,
     whatever the version.
   - **Refusal:** every spawn, resume, fork and cloud start answers 422 `claude_version` with that message and starts
     nothing (contract request S-03.10).
4. **Docs.** `docs/runner/built-ins.md` lists which Claude Code feature the runner uses for what (the items under
   "What stays as it is" below, plus the three above), linked from `docs/runner.md` with one line.

What stays as it is (checked on main, 2026-10-13):
- **Session state** comes from `claude agents --json --all` already (`Sessions.roster`, `normalise`, including
  `waitingFor` as `waiting_for`). The runner's state file only adds what Claude Code doesn't know: role, task, model,
  permission mode. No change.
- **Steering** stays hub → channel. `SendMessage` and `ListAgents` are tools *inside* a Claude Code session; there is
  no CLI command the runner could call, and the runner's scrubbed environment removes the `CLAUDE_CODE_MESSAGING_*`
  variables a script would need. The brain and workers refuse cross-session messages (ADR-003, step 1), so the hub
  sees every message.
- **No Notification hook.** Approvals already come both ways through the channel's permission relay
  (`permission_request` → approval card + push, S-04.6, S-08.1), and the runner reports `blocked` with
  `waiting_for` every 2 s (`needs_you`, task-states.md). A `Notification` hook is one-way, would duplicate both,
  and needs a new hub route. Revisit only if SP10 finds a prompt the channel does not relay (a login or a trust
  dialog). Then the hook posts it the way S-05.8's session-end hook does.
