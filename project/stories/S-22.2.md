# S-22.2 — One public address

`https://marcel-bot.com` is a constant in four places: `hub/src/marcel_hub/auth/tokens.py:27` (`DEFAULT_HUB`, in every
pairing link), `hub/src/marcel_hub/cloud.py:74` (`REPORT_URL`, given to every cloud quest),
`plugins/marcel/scripts/adopt.py:43` and the worker-protocol skill. Each install has its own address (ADR-013).

do:
1. Hub setting `public_url` (e.g. `https://mac.tail1234.ts.net`; `MARCEL_PUBLIC_URL` or `marcel.toml`). Pairing links
   use `<public_url>/api`; cloud prompts use `<public_url>/api/session/report`. Unset: the hub starts, says once in
   its log "No public address yet: run `marcel connect`", and `pair` refuses with that sentence. The owner's NUC sets it
   to `https://marcel-bot.com` in `deploy/docker-compose.yml` (`MARCEL_PUBLIC_URL`) in this story, so pairing and cloud
   reports keep working there.
2. `adopt.py` reads `~/.marcel/hub-url` (as today) and has no built-in default; without the file it says "Run
   `marcel connect` first". The install (S-22.5) and `marcel connect` (S-22.8) write the file.
3. Worker-protocol skill: the report address is the one in the quest's first message, never a literal domain. Cloud
   quests retry a failed report every 1, 2, 4 … minutes for up to an hour (a sleeping Mac, B-51), then give up and say
   so in their final message.
4. `docs/operating.md`: the `public_url` row in the settings table.
done when:
- [ ] `grep -rn "marcel-bot.com" hub/src plugins/marcel --include=*.py --include=*.md` prints nothing outside tests and
      `docs/`.
- [ ] Tests: a pairing link and a cloud prompt carry the configured address; `pair` without `public_url` fails with the
      sentence above; `adopt.py` without `~/.marcel/hub-url` exits 1 with its sentence.
