# S-04.18 — Hub: tell the owner when Claude Code is logged out, when it is back, and why usage is stale

runner-api 0.1.13 `Health.login {state, since?, message?}` and `UsageReading.reason` (S-02.12); the runner fills it after S-03.13. On
2026-10-13 Claude Code on the NUC was logged out for about two hours and nothing told the owner. After S-04.17,
because both change `claude_updates.py`, which since S-04.17 reads the runner's `GET /health` only once at start-up.

do:
1. Bring back a look at `GET /health` every 60 s in `claude_updates.py` (S-04.17 kept only the one at start-up, in
   `_first_look`), for `login` only: the version change stays on the runner's events. Read `login` before any early
   return on an empty version (a runner whose `claude` cannot run may still say the login is lost). A failed look is
   skipped quietly; the next one tries again. No `login` (a runner older than 0.1.13) or
   `unknown`: say nothing.
2. **`lost`:** one notice in the owner's main conversation, pushed with level `urgent`
   (`pusher.note(..., 'urgent', OWNER)`; its hourly cap is shared with the version notices), once per
   `login.since`: the runner's `message` as it is, e.g. "Claude Code on the NUC is logged out. Log in again: on the NUC run
   `claude auth login`." A `lost` with a `since` already told is never told again, also after a hub restart (kept in
   `<data_dir>/claude-version.json`, next to what the hub keeps for version changes).
3. **Back to `ok` after a told loss:** one short notice, not pushed: "Claude Code on the NUC is logged in again; new
   work can start." Nothing when no loss was told.
4. `GET /internal/health` (`path_health.py`): the `runner` block carries the runner's `login` when its state is not
   `ok` (a missing `login` is left out). It never changes the runner's `state` (`ok` stays `ok`), so a redeploy is never rolled back over a lost login.
5. **Why usage is stale**, also in `claude_updates.py` (it has the database, the pusher and the told login loss; the
   usage guard in `usage.py` has none of them): on each look also call `runner.usage()` (`runner_client.py`;
   `None` or an error: skip) and read `reason`. When a stale reading brings a
   `reason` the hub has not told yet, one plain notice in the owner's main conversation, not pushed: "Marcel cannot
   read plan usage right now: <reason>". Nothing when `reason` is the message of a login loss already told (same
   words, step 2), so the owner never hears the same thing twice. Told again only after a good reading came in
   between.
6. In `hub/tests/test_runner_client.py`, move `Health.login` and `UsageReading.reason` from `PENDING_RUNNER_FIELDS`
   to `RUNNER_FIELDS_KNOWN`.
7. Docs: `hub/README.md` § "When Claude Code changes under Marcel" (the login and stale-usage notices) and
   § "Whole-path health" (`login`) say what the hub now does.

done when:
- [ ] Test (fake runner): `lost` on three looks in a row gives exactly one urgent push and one message; deleting the
  "once per `since`" check fails the test.
- [ ] Test: a hub restarted during the same loss (same `since`) sends nothing; a new loss (a later `since`) is told.
- [ ] Test: `ok` after a told loss gives one "logged in again" notice, not pushed; `ok` with no loss before gives
  none; a missing `login` and `unknown` give none.
- [ ] Test: `/internal/health` with a lost login answers runner `state` `ok` and shows `login`.
- [ ] Test (fake runner, `claude_updates.py`): a stale reading with a new `reason` gives one notice; the same `reason` again gives none; the
  told login loss's message as `reason` gives none; a good reading and then the same `reason` gives one again.
- [ ] `make -C hub check` green with `PENDING_RUNNER_FIELDS` empty.
