# S-08.1 — Notifier interface, ntfy backend, routing

do:
1. Define `Notifier.send(device, notification)`, where `notification` is the contract's
   `PushNotification` (title, body, category, level, deep link, collapse key, task and approval
   ids), with two backends: ntfy (HTTP POST to a topic on a configurable server, mapped as the
   contract describes, Click = the deep link, never a token) and APNs (S-08.2).
2. Routing policy, from task and hub events to a `PushNotification`:
   - an open approval → category `approval`, level `urgent`, deep link `marcel://approval/<id>`;
   - a task `needs_you` without an approval (a question, a login) → `task`, `urgent`;
   - a task `done` or `failed` → `task`, `normal`;
   - a task `silent`, the runner unreachable, or a failed push of an urgent message → `broke`, `urgent`;
   - a digest → `digest`, `normal`.
   Never send on progress.
3. `GET /me` reports `push.ntfy` and `push.ntfy_server` from the configuration.
4. Rate limits:
   - collapse repeats per task;
   - one "broke" per cause per hour;
   - a failure to send is logged, never raised into the caller.
done when:
- [ ] Routing table test: each event above maps to the right category, level and deep link, and
  every notification validates against `PushNotification`.
- [ ] Test: the ntfy backend posts the right payload (`respx`).
- [ ] Test: a dead ntfy server does not break task processing.
