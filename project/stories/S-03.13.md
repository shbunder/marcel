# S-03.13 — Runner: say when Claude Code is logged out, and why usage is stale

runner-api 0.1.13 `Health.login {state, since?, message?}` and `UsageReading.reason` (S-02.12). Found live on the NUC on 2026-10-13: after a
Claude Code self-update the supervisor could not refresh its login ("headless daemon cannot complete OAuth … no token
found") for about two hours; no session started, `/usage` failed, and `/health` still said `ok`.

do:
1. **Look first, on the NUC.** Find the failure lines of 2026-10-13 in `~/.claude/daemon.log` and run
   `claude auth status --json` (it prints `loggedIn`, `authMethod` and account details on 2.1.290; check it does the same on the pinned
   version in `runner/claude-version`). Copy
   the failure lines and one logged-in and one logged-out `auth status` answer, with the email, org and ids replaced
   by placeholders, into `runner/tests/fixtures/login/`. Write in `project/lessons/runner-built-ins.md` which source
   showed the failure, and the exact failure text.
2. **`login.py`** decides the state, at most once per 30 s (as `health.ClaudeProbe`: a `/health` between two looks
   gets the last answer; `claude auth status` takes about 0.6 s, with a 3 s timeout):
   - `lost` when `claude auth status --json` says `loggedIn: false`, or when a failure line (the pattern from step 1,
     e.g. `cannot complete OAuth` or `re-auth required`) was written to `daemon.log` since the last look (read from
     the byte offset of the last look, as `health.last_shutdown` does).
   - Back to `ok` from `lost` only when `auth status` says `loggedIn: true` and two looks in a row (60 s) found no new
     failure line, so a loss never flaps.
   - `unknown` when `auth status` cannot be run, times out or prints something that is not that JSON, and no failure
     line is new.
3. **`since`** is the time of the look that first saw the state. It is kept in `login.json` in the runner's state folder
   (next to `sessions.json`), so a runner restart during a loss keeps the same `since` and the hub does not tell the
   owner twice. An unreadable `login.json` starts afresh; it never stops the runner.
4. **`message`**, in plain words: `lost` "Claude Code on the NUC is logged out. Log in again: on the NUC run
   `claude auth login`." (use the command that worked in step 1 if it was another); `unknown` "The runner could not
   check whether Claude Code is logged in." Never the email, org or a token.
5. `collect_health` takes the login checker as an optional argument and adds `login` when it is given; it never
   changes `ok` or `reason` (runner-api `Health.login`). Only the `/health` route in `server.py` passes it, so
   `sessions.py` (which calls `collect_health` before each start) stays as it is and a start never waits for
   `claude auth status`. The shared fake `claude` in `runner/tests/conftest.py` learns `auth status --json`
   (logged in by default).
6. **`UsageReading.reason`** (`usage.py`): when the latest read fails, `reason` is its `UsageUnreadable` message;
   cleared on the next good read; never on a fresh reading. The cost-view failure (`COST_VIEW`, a logged-out Claude
   Code) also tells `login.py` the login is lost (as a new failure line does), and its `reason` is then the login's
   `message`, word for word, so the owner reads one sentence in both places. Before the first good read `/usage`
   answers 503 `no_reading`, which has no `reason`: then only `/health` `login` tells the hub, which is enough.
   `reason` never carries an email, org name or token from what `claude` printed (cut them, or say it in own words).
7. Docs: `docs/runner/built-ins.md` gets a row for the login check; `docs/runner/usage.md` says `reason`.

done when:
- [ ] Test (fixtures from step 1, a fake `claude`): logged out gives `lost` with `since` and `message`; a new failure
  line in a sample `daemon.log` gives `lost` while `auth status` says logged in; one clean look after it is still
  `lost`, two give `ok`; `auth status` failing gives `unknown`.
- [ ] Test: a restarted runner (a new checker on the same state folder) keeps the loss's `since`.
- [ ] Test: `ok` stays true with `login.state` `lost`; every `/health` answer the tests make validates against
  runner-api.yaml `Health`.
- [ ] Test (`usage.py`): a failed read after a good one gives `stale: true` with `reason`; the next good read drops
  it; the cost-view fixture gives the login's `message` as `reason` and `login.state` `lost`; every reading validates
  against runner-api.yaml `UsageReading`.
- [ ] Test: no `email`, `orgId` or `orgName` value from the fixture appears in any `/health` or `/usage` answer.
- [ ] On the NUC, `curl --unix-socket ~/marcel/run/runner.sock http://runner/health` shows `"login": {"state": "ok", …}`.
- [ ] `make -C runner check` green.
