# S-02.12 — Contract: the runner says whether Claude Code is logged in, and why usage is stale

Lead only. runner-api 0.1.12 → 0.1.13, additive. Found live on the NUC (2026-10-13): after a Claude Code self-update
the supervisor's login refresh failed ("headless daemon cannot complete OAuth … no token found") for about two hours.
No session could start and `/usage` failed, but nothing told the owner; it only showed as stale usage. Also answers
`project/contract-requests/S-03.7-usage-reason.md`.

do:
1. **`Health.login`** (optional) `{state, since?, message?}`. `state` is `ok | lost | unknown`. `since` is when the
   runner first saw that state; required with `lost`, so the hub tells the owner once per `since`. `message` is plain
   words, e.g. "Claude Code on the NUC is logged out. Log in again: on the NUC run
   `claude auth login`."; required with `lost` and `unknown`.
   No other fields: the account's email or plan never leave the runner. A runner older than 0.1.13 sends no `login`:
   the hub reads that as `unknown`.
2. **`ok` stays as it is.** `lost` does not set `Health.ok` to false on its own. `deploy/health.sh` and the hub's
   `/internal/health` read `ok` to decide a redeploy rollback, and rolling back a good merge cannot log anyone in.
3. **No runner event.** `GET /health` alone: the hub reads it once at start-up (`claude_updates.py`, after S-04.17),
   and S-04.18 adds one look a minute, a cheap socket call. A hub that starts during a loss needs that read anyway, and
   a minute's delay does not matter for a problem that waits for a person.
4. **No app-api change.** The owner hears through the hub's pushed notice in their main conversation (S-04.18). The
   app's `GET /health` needs no token and is reachable through the tunnel, so it should not tell anyone whether the
   account is logged in.
5. **`UsageReading.reason`** (optional, S-03.7): why the latest attempt to read usage failed, in plain words. Set
   only then, so only with `stale` true (an if/then rule); absent when that attempt worked. When the cause is a lost
   login (`/usage` shows the pay-as-you-go cost view) it is the same words as `Health.login.message`, and the runner
   counts that as `login.state` `lost` too. One message, one state, two places.
6. **Hub pending lists.** `Health.login` and `UsageReading.reason` go on the new shrink-only `PENDING_RUNNER_FIELDS`
   in `hub/tests/test_runner_client.py`, next to `RUNNER_FIELDS_KNOWN` (the fields of both schemas the hub reads or
   leaves alone). A new field the hub has not placed in one of the two fails the hub gate.

Deferred:
- **A 422 `logged_out` on a start while the login is lost.** Claude Code's own error reaches the hub today; a clearer
  refusal is a later contract change if the brain needs it.
- **Showing the login on the app's status screen.** Only behind a token (`GET /me` or a new route), if the owner asks.
- **Why usage is stale on the app's usage screen** (an app-api `Usage` field). The hub tells the owner in the chat
  instead (S-04.18); the screen can follow if the owner wants it there.

done when:
- [ ] `contracts/tests/test_contract_s02_12.py` covers each state, each required field per state, a bad `since`, an
  extra field, that `ok` may stay true with `lost`, and that `UsageReading.reason` is refused on a fresh reading; `make -C contracts check` and `make -C contracts mutants`
  green.
- [ ] `make check` green with `PENDING_RUNNER_FIELDS = {'Health': {'login'}, 'UsageReading': {'reason'}}`.
- [ ] `project/contract-requests/S-03.7-usage-reason.md` is deleted.
