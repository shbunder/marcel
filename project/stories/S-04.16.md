# S-04.16 — Hub: show a workflow's steps

transcript.schema.json's four workflow types and `workflow_id`, app-api 0.7.3 `TaskEventType` (S-02.11). The runner
streams them after S-03.11.

do:
1. Add `workflow_start`, `workflow_stop`, `workflow_agent_start` and `workflow_agent_stop` to `TRANSCRIPT_DATA`,
   `workflow_id` to `TRANSCRIPT_FIELDS` (checked against the run id pattern), and the four values to
   `models.TaskEventType`. Remove them from `PENDING_TRANSCRIPT_TYPES`, `PENDING_TRANSCRIPT_FIELDS` and
   `PENDING_ENUM_VALUES` (the pending tests then go red if any is left).
2. A `workflow_start` on a task's main tail opens one more tail, `?workflow=<run_id>`, for that task, with its own
   stored offset (keyed by session and run), the same resume, backoff and start-over rules as the main tail. Its events
   are stored as the task's events. It ends when the task ends or after the run's `workflow_stop` and the journal has
   nothing new for one poll.
3. The hub does not open the per-agent `subagent=` tails: the journal's start and stop per agent is what the quest
   view shows, and ten agents' tool calls would flood it.
4. Docs: `hub/README.md` says what a workflow adds to a quest.

done when:
- [ ] Test (fake runner): a `workflow_start` opens the journal tail; its `workflow_agent_*` events land as task events
  in order; a hub restart resumes the journal tail from its stored offset without storing an event twice.
- [ ] Test: a bad `workflow_id` or an unknown field is logged and dropped, never stored.
- [ ] `make -C hub check` green with the pending lists empty of workflow entries.
