# S-22.4 — The marcel command and its services, on both systems

One command, `marcel`, replaces `make -C deploy …` and knows how to run Marcel's background services on macOS
(LaunchAgents, no admin) and Linux (`systemd --user`). Read first: `plan/05-install-anywhere.md` § 4,
`scratch/spikes/SP11-mac-services/RESULT.md`, today's units in `deploy/systemd/`.

do:
1. `deploy/cli/` — a small Python 3.12 package `marcel_cli` (stdlib only, run with `uv run --project deploy/cli`),
   with a `marcel` entry point. `~/.marcel/bin/marcel` is a two-line launcher that the install puts on the PATH hint.
2. One **service table** (name, command, environment, keep-alive, start-after, schedule or watched path, systems):
   `claude-daemon` (**Linux only**), `runner`, `hub`, `backup` (nightly 03:30 UTC), `redeploy` (runs when
   `~/.marcel/state/redeploy.flag` changes), `tunnel` (filled by S-22.8). On a Mac there is no `claude-daemon`
   service: Claude Code starts its supervisor on demand from the runner's first `claude --bg` and has turned its
   service install off, and a `KeepAlive` job would fight the user's own `claude` for it (SP11 RESULT.md steps 2 and
   4; ADR-013 question 5 as amended). The Mac `runner` row's environment: `MARCEL_HOME`, `MARCEL_CLAUDE` (absolute
   path to the user's `claude`), `MARCEL_RUNNER_SOCK` (`$MARCEL_HOME/run/runner.sock`), and a `PATH` with node 22
   first (the plugin runs a bare `node`; launchd's default `PATH` has none). The on-demand supervisor inherits this
   environment. S-22.6 adds `MARCEL_CLAUDE_PIN=off` to the same row. If SP11 step 2 shows the supervisor in the runner
   job's process group, the runner plist sets `AbandonProcessGroup` (S-22.3 checks it). From the table:
   - macOS: `~/Library/LaunchAgents/com.marcel.<name>.plist` (`KeepAlive`, `StartCalendarInterval`, `WatchPaths`,
     logs in `~/.marcel/logs/`), loaded with `launchctl bootstrap gui/<uid>`;
   - Linux: `~/.config/systemd/user/marcel-<name>.service|.timer|.path`, generated with the same contents as the
     files in `deploy/systemd/` today, **with the same names** (`marcel-claude-daemon.service`, …), so the NUC's running
     units are replaced in place and never restarted by the swap. `deploy/systemd/` stays until S-22.5 switches
     `install.sh` over (it copies from there today); the generated ones keep the `marcel-v3-unit` marker.
   - **Docker mode** (the NUC until S-22.24): a `marcel-hub` Docker container exists **and** `~/.marcel/state/native`
     does not. In Docker mode the `hub` service is not enabled, so a redeploy never starts a second hub on port 7420.
     `marcel migrate` (S-22.24) writes `state/native`; its move-back deletes it.
3. `marcel start|stop|status|logs [service]`. `status` prints one line per service, and on a Mac one more for Claude's
   supervisor, read-only from `claude daemon status` ("Claude's supervisor: running, 2.1.300, shared with your own
   sessions" or "not running; it starts with the next quest"). Linux: `stop` never stops `claude-daemon` unless
   `--all` is given, and says that this ends every session. macOS: `marcel` never stops Claude's supervisor at all.
4. Linux: `marcel services install` tries `loginctl enable-linger $USER` without sudo; if it fails it prints the one
   sudo line and carries on.
5. The `redeploy` service runs `deploy/redeploy.sh` exactly as today; nothing in `marcel` restarts the hub, the
   runner or the supervisor on its own behalf except `start|stop` typed by a person (self-modification rule).
6. Docs: S-22.5 owns `docs/operating.md` for the native install; this story adds the service table's description to
   `deploy/cli/README.md` (in `touches:` through `deploy/cli/`).
