# S-22.15 — The hub pushes through the relay

A third `Notifier` next to ntfy and APNs (`hub/src/marcel_hub/notify/backends.py`), for phones whose push target is
`kind: relay` (app-api 0.8.0).

do:
1. `RelayNotifier`: seals a `SealedPushContent` (`{title, body, link, agent_id?, category?}`) for the device's `device_key` exactly as `SealedPush` says
   (X25519, HKDF-SHA256 `marcel-push-v1`, ChaCha20-Poly1305, with `cryptography`, already a dependency), and posts it
   to the device's `relay_url` with its `send_secret`. 410 → the device's push target is cleared, so `Device.push` reads
   `none` and the phone registers again (S-02.13). Timeouts and 5xx are retried as the other backends do.
2. `PUT /devices/{id}/push` accepts `kind: relay` and stores `relay_url`, `handle`, `send_secret` (never shown) and
   `device_key` (migration). `PushTarget` is not a stored model, so `test_contract.py` has no `PENDING` entry for it.
3. Always on: no hub setting; the relay address comes from the phone. `Me.push.relay` is `true`.
4. `hub/README.md` § Push: the relay, what it sees, and that `MARCEL_APNS_*` is only for the owner's own builds.
5. Lead decision (2026-10-24, follow-up from S-22.27): an approval push for a buddy that no phone shows right now goes to
   every phone (`Pusher._devices`), so an approval never waits silently. Other buddy pushes still go only to the
   phones showing that buddy.
done when:
- [ ] Tests: the sealed bytes match the contract's known-answer vector for its fixed keys; a 410 clears the target;
      the relay never receives the plain text (the test inspects the fake relay's request body).
- [ ] Test: an approval for a buddy no phone shows reaches every phone, and the test goes red without the fallback;
      a non-approval push for that buddy still reaches no phone.
