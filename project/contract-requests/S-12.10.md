# Contract request — S-12.10 (settings, notifications, deep links)

S-12.10 worked around these; nothing in `contracts/` was changed.

1. **Project and artifact deep links** (`app-api.yaml` `PushNotification.deep_link`). The story routes
   `marcel://project/<slug>` and `marcel://artifact/<id>`, and `Project.slug` says it is "used in
   `marcel://project/<slug>`", but the push's `deep_link` pattern is `^marcel://((task|message|approval)/[A-Za-z0-9_-]+|status)$`,
   so the hub may never send them in a push. The app accepts both (from the ntfy app, Safari or another app).
   Proposed: `^marcel://((task|message|approval|artifact)/[A-Za-z0-9_-]+|project/[a-z0-9][a-z0-9-]{0,39}|status)$`,
   and list both in the description.
2. **One approval by id** (`GET /approvals/{approval_id}`). `marcel://approval/<id>` needs the approval's task; the
   app reads the whole `GET /approvals` list to find it, which misses an approval the list no longer returns.
   Proposed: `GET /approvals/{approval_id}` → `Approval` (404 `approval_not_found`).
3. **One message by id** (`GET /messages/{message_id}`). `marcel://message/<id>` can only be placed when the message is
   already in the phone's cache; a push that outruns the live stream lands on the latest messages instead. Proposed:
   `GET /messages/{message_id}` → `Message`, so the app can tell the main conversation from a side thread and cache it.
4. **Push action identifiers.** The description says an `approval` push "has Approve and Deny actions" but does not
   name them. The app registers `approve` and `deny` on the `approval` category. Proposed: name them in the
   description, so a hub-side APNs test can use them.
