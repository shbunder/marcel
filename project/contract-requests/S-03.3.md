# Contract request — S-03.3 (state watcher and `/events`)

**Answered by the lead (PR #39 review).** The lead changes `contracts/runner-api.yaml` to: "On every
connect: with a resumable `Last-Event-ID`, the events after it first; then always one
`session.state` per known session, all carrying the newest `seq`. Event ids do not start at 1." and
adds a `runner.recovered` event. The runner follows that wording. No hub change is needed: the hub
ignores a state it already has.

What was asked, for the record:

1. The contract said every connect starts with one `session.state` per known session; the story said
   a reconnect gets no duplicates. The answer: missed events first, then the fresh view, always. The
   fresh view comes last, so a hub that marked its tasks `unknown` during a short outage gets them back.
2. Event ids start at the runner's start time in milliseconds, so an id from before a restart is never
   resumed. Answered: "Event ids do not start at 1."
3. The hub had no way to clear its `runner_warning` alert. Answered: `runner.recovered`, sent once on
   the first good poll after a warning.
