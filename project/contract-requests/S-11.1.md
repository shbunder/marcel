# Contract requests from S-11.1 (self-change tasks and approval)

The hub follows the contract as written; these are gaps or wording that ADR-005 (the owner merges self-changes on
GitHub, the hub never merges) leaves out of date.

1. **`Approval.artifact_id` (app-api.yaml).** It says "For `self_change`, the PR artifact that approving will
   merge." Approving no longer merges (ADR-005). Suggested: "For `self_change`, the PR artifact this card is
   about. Approving is the owner's go-ahead; the owner merges the PR on GitHub, and only a PR both approved here
   and merged is redeployed."
2. **A system event for a self-change answer (channel.schema.json `SystemEvent.kind`).** The lead asked that a
   denial be told to the brain as a system event, so the brain or a worker can close the PR with its own git
   credentials. `SystemEvent.kind` has no fitting value, so the hub sends the task that made the PR a `steer`
   (author `marcel`) instead, which the contract allows. Suggested: add kind `self_change` with
   `data: {artifact_id, url, decision: approved | denied | merged_unapproved | redeploy_requested, note?}`, so
   the brain can tell the owner and act when the task that made the PR has stopped or failed (today such a task
   gets nothing and the owner closes the PR on GitHub).
3. **`self_change` as a prompt's tool name (channel.schema.json `PermissionRequest.tool_name`).** A worker's
   permission prompt may name any tool, including `self_change`; the hub then stores a card with
   `tool: self_change` and no `artifact_id`, which breaks `Approval`'s own `if tool = self_change then
   artifact_id` rule. The hub never treats such a card as a self-change (it has a `request_id`), but the card it
   serves is off-contract. Suggested: reserve `self_change` in `PermissionRequest.tool_name` (the hub refuses or
   renames it).
