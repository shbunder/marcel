# Contract request — S-06.6 (project-aware routing)

S-06.6 step 3 says workers append durable facts to their project's notes "through `report(note)`, which the
hub writes to `memory/projects/<slug>.md`" (B-33). The contracts have no such report kind, so S-06.6 leaves
that step out: the `worker-protocol` skill does not mention it, and nothing in `contracts/` was changed.
The brain tools, the `orchestrate` skill and the brain persona (steps 1, 2 and 4) are done.

## What is missing

`report`'s `kind` is `started | progress | artifact | done | failed` in both places a worker reports:

- `contracts/channel.schema.json` `$defs.Report.properties.kind` (NUC workers, through the channel).
- `contracts/session-api.yaml` `Report.properties.kind` (cloud workers, `POST /api/session/report`).

A worker has no other way to write memory: the brain tools (`memory_write`) refuse a worker's session.

## Proposed

1. Add `note` to both enums, with `text` required (`if kind == note then required: [text]`), at most
   1 000 characters: one fact a later thread in the same project needs ("The Luminus contract ends on
   1 March 2027"), in plain words.
2. Say what the hub does with it, in `Report`'s description: append `- <date> <text> (from <task title>)` to
   `memory/projects/<slug>.md` of the task's project (the Inbox's notes for an unfiled task), commit it as
   `memory: projects/<slug>.md (worker <task id>)`, and record no milestone in the main chat. A note never
   changes the task's state.
3. Limits the hub enforces (so a chatty worker cannot bloat the notes every thread starts with): at most
   10 notes per task; past that `report` answers an error that says so.

When this lands, a small follow-up story adds `note` to the `worker-protocol` skill (its lint already
checks that every report kind it names is in the contract, and that it explains every kind the contract
has, so the skill and the contract cannot drift apart).
