# Contract request — S-06.2 (brain keep-alive and rollover)

S-06.2 worked around these; nothing in `contracts/` was changed.

1. **The brain's context size.** The story asks for a rollover "when the brain's context passes a threshold", and
   `events.schema.json` `BrainRollover.reason` has `context_full`. The hub cannot see how full the context is:
   `transcript.schema.json` carries no token counts (no `usage` on `text` or `turn_end`), and runner-api.yaml
   `Session` has none either. So the hub rolls over nightly, on a crash and on request only. Proposed: the runner
   adds `usage: {input_tokens, cache_read_input_tokens, cache_creation_input_tokens, output_tokens}` to the
   transcript's `turn_end` data (Claude Code writes `message.usage` on every assistant line), so the hub can
   roll over past, say, 70 % of the model's context window.
2. **A manual rollover from the app.** `reason: manual` exists, but app-api.yaml has no route to ask for one.
   `BrainKeeper.roll_over(agent_id)` is ready behind it. Proposed: `POST /agents/{agent_id}/rollover` → 202,
   owner only, 409 `rollover_running` while one is waiting for its hello.
3. **Past rollovers** (also S-12.9's first request). The hub stores `brain.rollover` only as an app event, and the
   event log keeps the latest 2000 per user, so it cannot serve `GET /agents/{agent_id}/rollovers` from storage
   as it is. With that route, the hub would add a small `brain_rollover` table (id, agent_id, at, reason, kept),
   written in the same place the event is published: not trivial, but small.
4. **channel-protocol.md, "Brain and side-thread ids".** It says the hub accepts a brain only when
   `Conversation.brain_session_id` holds its id. A rollover adds one case: the new brain the hub started is
   accepted at its hello, which makes it the conversation's brain (the hand-over), and is refused
   `unknown_session` while the old brain is mid-turn (the server's 5 s retry brings it back). Proposed: say so
   there, and that a `reply` from a replaced brain is answered `call_ack.error` with code `replaced`.
5. **A reply refused with `replaced` loses the old brain's answer.** After a hand-over the hub refuses a `reply` from
   the replaced session (`call_ack.error`, code `replaced`), and the channel server drops it, so whatever the old
   brain was saying is gone. The hub keeps this rare (it hands over only between turns, by the runner's state and
   its own turn tracking, and re-sends unanswered owner messages to the new brain), but cannot make it impossible:
   the old brain can start a turn of its own (a system event) in the moment of the hand-over. Proposed: the
   protocol defines `replaced`, and says what happens to the refused text: either the hub stores it marked as
   from the retired session (shown greyed in the app), or the server hands it to nobody and says so in the
   session's tool result. Today it is only logged.
