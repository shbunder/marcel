# Contract requests from S-03.6 (cloud spawn and send)

Against `contracts/runner-api.yaml` 0.1.6. The runner follows the contract as written; these are
gaps it had to fill.

1. **No `400` on `spawnCloudSession` or `sendCloudMessage`.** A body that is not `{prompt}` /
   `{text}`, or a path id that does not match `^session_[A-Za-z0-9]+$`, answers
   `400 bad_request`, as every other runner operation does. Add the `400` response to both.
2. **No timeout or "claude missing" response.** Other operations use `503 claude_timeout` /
   `claude_unavailable`. For the two cloud operations the runner keeps to the listed `422`
   (`cloud_unparsed` / `cloud_send_failed`) with a plain message ("did not create the cloud session
   within 60 s …"). Either list those cases under the `422`, or add the usual `503`.
3. **No `cwd` or repo in the create request.** `claude --cloud` takes its repo from the folder it
   runs in (SP3 ran it from the marcel checkout). The runner runs it in its home folder, so a cloud
   task cannot choose its repo. Suggest an optional `cwd` (absolute, existing folder), or a `repo`
   that reuses `RepoSpec` and the workspaces clone.
4. **`url` is documented only by example.** The runner hands back `https://claude.ai/code/<id>`
   with Claude's `?from=cli&m=0` dropped, and refuses any other host. Say so in `CloudSpawned.url`
   and `CloudAck.url`, so the hub can rely on it for `cloud_url`.
