# Contract requests from S-05.4 (/marcel-adopt)

Against `contracts/session-api.yaml` and `contracts/app-api.yaml`. The hub follows the contract as
written; these are gaps it had to fill.

1. **No location for "a computer that is not the NUC".** `TaskLocation` is `nuc | cloud`. A local
   session adopted from a laptop is stored as a `nuc` task (with `tracked: links_only`), so the app
   says "NUC" and, when the runner goes down, the hub marks it `unknown` with the real NUC tasks.
   Add a value such as `elsewhere` (a local session on another computer, followed by link only), or
   say in `TaskLocation` that `nuc` also covers it.
2. **`AdoptRequest` has no `model`.** `Task.model` is required, and the session knows its model;
   the hub stores `unknown`. Add an optional `model` to `AdoptRequest` (the script can read it
   from the session's settings when Claude Code exposes it).
3. **No agent to adopt into.** `AdoptRequest` names no agent, so the hub files the task with the
   owner's first agent (lowest id). When a second agent arrives, add an optional `agent_id` (or
   say in the contract that the first agent takes adopted sessions). A hub with no agent at all
   answers `400 no_agent`; the contract lists only 400/404/429, so say that a 400 can also mean
   "this hub cannot adopt yet".
4. **The session id for a cloud session.** The contract says `session_…` for a cloud session but
   not where a session finds its own. The script reads `CLAUDE_CODE_REMOTE` (cloud or not) and
   `CLAUDE_CODE_REMOTE_SESSION_ID`; neither is confirmed in a spike. Note it in SP3 or in the
   contract's description once a live cloud run confirms it.
