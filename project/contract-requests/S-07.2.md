# Contract requests from S-07.2 (cloud report endpoint)

Against `contracts/session-api.yaml` 0.1.4. The hub follows the contract as written; these are gaps
it had to fill.

1. **A report has no id, so a retry cannot be told from a new report.** A worker whose connection
   drops after the hub stored its report sends it again, and the owner would see a second
   "started" milestone or a second note. The hub fills the gap by itself: the same report (the same
   JSON, key order aside) from the same task within 10 minutes is answered 202 and stores nothing.
   That memory is lost on a hub restart, and two genuinely identical progress lines ten seconds
   apart are taken once. Proposal: an optional `report_id` (string, at most 64 characters) on
   `Report`; the hub answers 202 and stores nothing for a `report_id` it already took for that
   task, and the worker protocol in the prompt tells the worker to send one.
2. **429 on wrong tokens shows the route exists.** The info block says `report` answers 429 when
   limited, while `adopt` answers 404 "because a 429 would show that the route exists". The hub
   does as written (429 `too_many_requests` for a caller past 10 wrong tokens a minute), but the
   reason given for adopt applies here too. Either keep 429 and say why the trade differs (a cloud
   worker should learn it is limited, not that its token is bad), or answer 404 as adopt does.
3. **Per-task flooding.** The contract names 429 only for wrong tokens. The hub also limits a good
   token to 30 reports a minute per task (429 `too_many_reports`), so a worker stuck in a loop
   cannot flood the owner's phone. Name that code under the 429 response.
