# Contract requests from S-07.2 (cloud report endpoint)

Against `contracts/session-api.yaml`. The hub follows the contract as written; these are gaps it
had to fill.

1. **Open: a report has no id, so a retry cannot be told from a new report.** A worker whose
   connection drops after the hub stored its report sends it again, and the owner would see a
   second "started" milestone or a second note. The hub fills the gap by itself: the same report
   (the same JSON, key order aside) from the same task within 10 minutes is answered 202 and stores
   nothing. That memory is lost on a hub restart, and two genuinely identical progress lines ten
   seconds apart are taken once. Proposal: an optional `report_id` (string, at most 64 characters)
   on `Report`; the hub answers 202 and stores nothing for a `report_id` it already took for that
   task, and the worker protocol in the prompt tells the worker to send one. It would also settle
   two cases the hub now handles only by guessing: the same report arriving twice at once (taken
   once by an in-memory mark), and a retried `done` whose first try was stored (today a 404,
   because `done` spent the token, so the worker cannot tell "stored" from "refused").
2. **Answered by session-api 0.1.5 (#92): 429 on wrong tokens.** A caller limited for wrong tokens
   now gets the hidden 404 on `/session/report`, as on adopt. The hub does that.
3. **Answered by session-api 0.1.5 (#92): per-task flooding.** 429 `too_many_reports` is named in
   the contract, only for a valid token sending too fast. The hub sends it past 30 reports a minute
   per task.

**Deferred (lead, S-02.10):** item 1 needs the hub to take a `report_id` first, so it waits for its own hub story; items 2 and 3 were answered by session-api 0.1.5.
