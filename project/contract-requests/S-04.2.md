# Contract request — S-04.2 (device pairing and auth)

Nothing blocks the story. These are gaps where the hub had to pick a behaviour.

## 1. Where `Me.name` comes from

**What.** `Me` requires `name`, but the data model has no user record: `device.user_id` and
`agent.owner_user_id` point at a user that is stored nowhere.

**What the hub does today.** There is one user, `usr_owner`. Pairing codes and devices belong to
them. `Me.name` comes from a new setting, `owner_name` (`MARCEL_OWNER_NAME`, default `Owner`).

**Proposed change.** Either say in `02-architecture.md` that Marcel has a single owner whose name is
a hub setting, or add a `user(id, name)` table to the data model.

## 2. Agents without a main conversation

**What.** `Agent.main_conversation_id` is required in the contract, but nullable in the data model
(an agent row can exist before its main conversation).

**What the hub does today.** `GET /me` leaves out agents that have no main conversation yet.

**Proposed change.** None needed if that is the intent; otherwise say who creates the main
conversation and when (S-04.3 or the agent-creation story).

## 3. Error codes the hub uses

**What.** `Error.code` is "stable, for code", but only `pairing_code_expired` appears in the
contract.

**What the hub uses.** `unauthorized` (401), `pairing_code_invalid`, `pairing_code_used`,
`pairing_code_expired`, `bad_request` (400), `device_not_found`, `not_found` (404),
`method_not_allowed` (405), `too_many_tries` (429, too many wrong pairing codes),
`internal_error` (500).

**Proposed change.** List them under `Error.code` so the app can match on them.

## 4. A 429 on `/pair`

**What.** `POST /pair` is public and lists only 201 and 400.

**What the hub does today.** After 10 unknown codes in a minute it answers 429 `too_many_tries`
with `Retry-After: 60`, so a live code cannot be guessed.

**Proposed change.** Add a `429` response to `/pair` with the `Error` shape.
