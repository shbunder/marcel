# Contract request — S-10.1 (usage guard)

S-10.1 worked around each of these; nothing in `contracts/` was changed.

1. **`GET /usage` before the first reading** (`app-api.yaml`). `Usage` requires `five_hour` and
   `weekly` with `used_pct`, and the path lists only 200 and 401. The hub has no numbers until the
   runner's first good reading (the runner itself answers 503 `no_reading` then), and none at all
   without a runner. The hub answers **503 `no_reading`** with the contract's `Error` shape rather
   than invent a 0 %. Proposed: add that 503 to the path (or make the windows optional and add
   `available: false`), so the app can show "usage unavailable".
2. **A push category for the usage guard** (`PushNotification.category`). "Marcel is pausing new
   work until 14:00: the subscription is at 91 %." goes out as `note`, `normal`, deep link
   `marcel://status`, collapse key `usage`. `note` is described as the brain's `notify` notices and
   `broke` as system faults; neither fits exactly. Proposed: a `usage` category (or say in the
   contract that `note` covers the hub's own plain notices too).
3. **Token counts for per-task usage** (`transcript.schema.json`, and a report in `app-api.yaml`).
   The story asks to attribute usage to tasks from transcript token counts, but the normalised
   transcript carries none (the runner drops `message.usage`). The hub now splits each rise of the
   five-hour window evenly over the tasks running then and keeps it in `usage-guard.json`
   (`UsageGuard.usage_by_task()`). Proposed: `text` (assistant) or `turn_end` events carry
   `tokens: {input, output, cache_read, cache_creation}`, and the app API gets a usage report
   (e.g. `GET /usage/tasks`, or `usage_share` on `Task`) to serve it.
4. **`/brain/usage` before the first reading** answers 503 `not_set_up` (the brain API's code for
   "built by a later story"). A `no_reading` code would say it better; it belongs with S-05.3's
   request to write the `/brain` API down.
