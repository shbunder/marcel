# Contract request — S-05.1 (channel server)

Nothing blocks the story. These are gaps where the server had to pick a behaviour. Each is small.

## 1. A repeated `permission_request` after a reconnect

**What.** `channel-protocol.md` says a server re-sends `reply` and `report` calls that have no `call_ack`. It
says nothing about `permission_request`, which has no ack.

**Why it matters.** The hub may drop the connection after Claude Code raised a prompt but before the hub stored it,
or after it stored it. Without a re-send the owner never sees the card.

**What the server does today.** It keeps every `permission_request` until its `permission_decision` arrives, and sends
it again after each welcome, with the same `request_id`.

**Proposed change.** Add to "Delivery guarantees": the hub treats a `permission_request` with an
`request_id` it already holds as a repeat, and does not open a second card.

## 2. What a tool call returns while the hub is down

**What.** The failure table says `reply`/`report` return "queued, Marcel is reconnecting"; the story says "returns
when `call_ack` arrives, or after 10 s with queued".

**What the server does today.** Connected: waits up to 10 s for the ack. Not connected: returns "Queued" at once and
keeps the call for the next welcome. After `bad_secret`, `plugin_too_old` or the end of the `unknown_session` window it
returns an error result ("Marcel is unreachable").

**Proposed change.** State this in the failure table.

## 3. `meta` for `steer` and `user_message` omits `handback` and `quoted_message_id`

The schema has `Steer.handback` and `UserMessage.quoted_message_id`. The mapping table gives a fixed `meta`
without them, so the server drops both. If the brain needs them, add `handback` and `quoted_message_id` to the table.

## Still open on `main` (2026-10-12)

The lead answered items 1–3 in `b2fdc87` ("[S-02.2] contract: runner pre-allows the plugin tools; channel repeats,
timeouts and settle delay"). That commit is on `claude/marcel-agent-orchestration-u6q6md` but never reached `main`,
so `main`'s `channel-protocol.md` and `runner-api.yaml` still lack it. The server already behaves as `b2fdc87` says.
On top of items 1–3, `main` is missing:

4. **Who pre-allows the plugin's tools.** `main` says the plugin's settings do it. They cannot: Claude Code keeps only
   `agent` and `subagentStatusLine` from a plugin's settings, so the PR has no `settings.json`. Proposed: the runner
   passes `--allowedTools mcp__plugin_marcel_marcel__reply mcp__plugin_marcel_marcel__report` on every spawn, fork
   and resume (as in `b2fdc87`).
5. **Settle delay.** The server holds hub frames, unacked, for 500 ms after `notifications/initialized`; a frame sent
   earlier can be lost (SP1).
6. **Hub silent.** No answer to hello within 15 s, or nothing for 60 s after welcome: the server closes and reconnects.
7. **Seq order.** The server ignores any `seq` at or below the highest it has delivered, so the hub must send in `seq`
   order, re-sends included.
