# Contract request — S-04.4 (task registry and state machine)

Nothing blocks the story. These are gaps where the hub had to pick a behaviour.

## 1. Stop when the runner is out of reach

**What.** `POST /tasks/{id}/stop` lists only 200, 401 and 404. Stopping a NUC task means asking the runner
first (`claude stop`). When the runner does not answer, the session may still be running.

**What the hub does today.** It answers **503** `runner_unreachable` ("The task was not stopped. …") and leaves
the task as it was. Marking it `stopped` anyway would hide a session that is still running and spending usage;
`stopped` is final, so the hub could never correct it later.

A side effect: a task in `unknown` (the runner is unreachable) cannot be stopped from the app until the
runner is back, because stopping it means asking the runner. So `unknown → stopped` only happens once the
runner answers again; until then stop answers 503.

**Proposed change.** Add a `503` response (`Error`, code `runner_unreachable`) to `stopTask`, and say in
`task-states.md` that `unknown → stopped` needs the runner back.

## 2. Error codes the contract does not name

**What.** The contract names `task_finished` for steer. The other task errors have no code.

**What the hub does today.** `404 task_not_found`, `409 task_not_finished` (archive on a task that is not done,
failed or stopped), `400 bad_request` (body or query does not match the schema).

`GET /tasks` lists only 200 and 401, but a request without `agent_id` (required), or with a bad `state`,
`archived`, `limit` or `cursor`, needs an answer: the hub gives **400** `bad_request`. `GET /tasks/{id}/events`
does the same for a bad `after` or `limit`.

**Proposed change.** List these codes next to the responses, so the app can match on them, and add `400` to
`listTasks` and `listTaskEvents`.

## 3. Where a task's opening prompt lives

**What.** `Task` has no prompt field, but a task queued for capacity must be started later with its prompt,
also after a hub restart.

**What the hub does today.** The prompt is stored as a `note` event, `author: marcel`, marked `prompt: true`;
the queue finds it by that flag. The queue is read from the database (`queued` with `queued_reason: cap`,
oldest first), so nothing is held only in memory, and the hub drains it once at start.

`NoteEventData` has `additionalProperties: false` and no `prompt` field, so the hub keeps the flag on the
stored row and leaves it out of what it sends the app. The same goes for a steer's `client_id`, which the
hub stores on the note to make a retried steer record and deliver once.

**Proposed change.** Add `prompt: boolean` ("the task's opening prompt") to `NoteEventData`, like `handback`,
and say that `author: marcel` also covers the opening prompt, not only `tasks_send`.

## 4. The `data` of a hand-back `system_event`

**What.** `channel.schema.json` `SystemEvent.data` is a free object.

**What the hub does today.** For `kind: handback` it sends `task_id`, a one-line `text`, and
`data: {title, state, note}` (`note` is `""` when the owner wrote none).

**Proposed change.** Document that shape for `handback`, so the brain's prompt can rely on it.
