# S-16.2 — Do we need a decision model? A first count

**Answer for now: no.** Brain turns that a typed decision could have handled used about **18 %** of the brain's
usage, under the story's 25 % line. But the sample is one night of test traffic, so count again after S-16.1 on at
least a week of the family's own use. The bigger cost was not decisions at all: **over half the brain's usage went
on starting fresh sessions and compacting.**

## What was counted

- **The window:** 2026-10-13 19:58 to 2026-10-14 05:28 UTC, from the first deploy on the NUC to the morning digest.
- **Who sent it:** every message came from build sessions (install checks, live tests, drills). None came from the
  family. This sample cannot show how real people use Marcel.
- **The sources:** 125 triage decisions (`triage.log`) and the transcripts of Marcel's brain (8 sessions) and Pip's
  (1). Both give 11 owner messages, 3 failed tasks, 2 task questions and 1 digest. One message arrived mid-turn as a
  `queued_command` and counts as its own turn. A Haiku probe someone typed into a brain folder is left out.
- **The measure:** tokens per turn, summed over the turn's model calls, each call counted once. Calls that leave no
  transcript entry (compaction, its recaps, a call cut off by a stop) are taken from Claude Code's own per-session
  `cost-state` record, as row F. Plan usage itself is not split by session, so the share is **weighted by Opus
  prices** (input 1, cache write 1.25, cache read 0.1, output 5) as a stand-in.

## The numbers

| Brain turns | Turns | Output tokens | Cache read | Weighted share | Share of event turns |
|---|---:|---:|---:|---:|---:|
| A. Status questions ("is anything waiting on me?") | 2 | 963 | 330 k | 6.8 % | 14.3 % |
| B. Follow-up → existing thread | 0 | — | — | 0 % | 0 % |
| C. Worker event the brain only relayed (2 questions, 3 failures) | 5 | 2 197 | 719 k | 11.5 % | 24.3 % |
| **A + B + C: a typed decision could have done these** | **7** | | | **18.3 %** | **38.5 %** |
| D. Needs the brain: start a quest (4), chat (5), digest (1) | 10 | 5 518 | 1 643 k | 29.1 % | 61.5 % |
| E. Start-up seeds (9) and compaction prompts (2) | 11 | 3 102 | 766 k | **42.0 %** | — |
| F. Calls with no transcript entry (compaction, recaps) | — | 2 786 | 602 k | **10.6 %** | — |

- **The share of event turns** leaves out E and F. Counted that way, A + B + C come to 38.5 %, over the line. The
  story asks for the share of brain usage, which includes them: 18.3 %.
- **A is slightly high.** The re-cache after a compaction (14 k cache-write tokens) fell in the first status question.
- **C overstates the saving.** All three failures were test tasks, so the brain only reported them. Its real job there
  is to decide retry, re-route or ask, which a rule cannot do. The push is already a rule (`notify/routing.py` decides
  whether to push and writes the push text); the brain writes only its chat reply. One failure turn (00:08) was cut
  off mid-call by a stop, so its reply is missing from the count.
- **B is 0 by design.** A reply in a task's own thread already goes straight to the task by rule (`thread_steer`); no
  follow-up was typed in the main chat this night.
- **Recognising a status question is the hard part.** The hub's own `status_question` rule (`triage.py`, a short
  regex) caught neither question: both start "Quick check…". So A was labelled by hand
  (`S-16.2-count/labels-2026-10-13.json`). Telling such a message apart in free text is exactly what a decision model
  would be for.

## What changes in the plan

- No follow-up story to pilot Clef through Workers AI. The owner's OK for a second paid API is not needed yet.
- After S-16.1, count again on a week of the family's own use: label the owner messages that are status questions or
  follow-ups in a new labels file, then `python3 turns.py <brain transcript folders> > t.json && python3 count.py
  t.json <labels>.json`.
- Worth a look first, though no story yet: start-up seeds were 9 of 28 turns, and seeds plus compaction were over
  half the usage that night. Four seeds followed an unexpected stop (deploys, and the 02:51 Claude Code
  self-update), two were first starts (Marcel and Pip), two were fresh starts on request (rollover drills) and one was
  the daily rollover. Each fresh brain re-reads its seed, and turns reload deferred tools (`ToolSearch` ran in 14 of 17
  event turns). Fewer restarts, or a smaller seed, saves more than a decision model would.
